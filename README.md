# Event ID 120 - Password Found in Requested URL: Possible LFI Attack


## Short Overview of the Investigation 🔬

This investigation examines a high-severity web attack alert generated by LetsDefend's SOC170 detection rule. An external IP attempted to access the Linux /etc/passwd file through a web request targeting a Windows server. The investigation focused on validating the malicious request, determining whether the attack succeeded, and deciding whether Tier 2 escalation was necessary.

*Investigation verdict*: True Positive - Malicious LFI attempt was unsuccessful.

## Investigation Steps 🕵️‍♂️

1. ### Alert Triage
I reviewed the alert metadata, source and destination IPs, requested URL, HTTP method, response code, and target server. The path traversal sequence ../../../../ suggested an attempt to access a file outside the application's intended directory.

2. ### Threat Intelligence and Log Analysis
I checked the source IP 106.55.45.162 using threat intelligence resources. It had a history of malicious activity. Firewall logs showed the inbound request was allowed, but the server returned HTTP 500 with a response size of zero bytes.

3. ### Endpoint and Attack Validation
I reviewed the target server's operating system and endpoint telemetry. The server was running Windows Server 2019, while the attacker attempted to access /etc/passwd, a standard Linux account file.

No endpoint activity confirming successful exploitation was identified in the reviewed logs. The HTTP 500 response and zero-byte response size supported the conclusion that the attempted file access did not succeed.

4. ### Attack Success and Tier 2 Escalation
I initially marked the attack as successful and selected Tier 2 escalation. Both answers were incorrect.

The evidence indicated that the attack was unsuccessful, and the playbook did not require Tier 2 escalation. The alert should have been be closed as a true positive after documenting the malicious attempt and appropriate response recommendations.


## My Findings, Conclusions, and Response

### Findings

- The source IP was associated with malicious activity.
- The request contained a path traversal payload targeting /etc/passwd.
- The inbound request was allowed by the firewall.
- The server returned HTTP 500 with no response body.
- The target ran Windows Server 2019, making the Linux-specific file path ineffective.
- No evidence of successful exploitation was identified in the reviewed logs.
- Tier 2 escalation was not required by the playbook.

### Conclusion 

This was a *True Positive unsuccessful LFI attempt*. The request was malicious, but the available evidence did not indicate successful file access or server compromise.

### Response

1. I restricted the malicious source IP.
2. I monitored web server logs for repeated path traversal and file inclusion attempts.
3. I reviewed application code to ensure user-controlled file paths are validated securely.
4. I considered web application firewall rules to detect and block common traversal payloads.
5. I documented the failed attempt and close the alert according to the playbook.

## Lessons Learned ✍️

- *Malicious does not mean successful*: An alert can represent a genuine attack attempt even when exploitation fails.
- *Interpret HTTP responses in context*: A 500 response and zero-byte body do not independently prove failure, but they support that conclusion alongside endpoint and server evidence.
- *Understand the target environment*: Linux-specific paths may not work on Windows servers.
- *Escalate based on evidence and playbook criteria*: Tier 2 escalation is not automatically necessary for every malicious request.
- *Learn from mistakes*: I achieved an 80% playbook success rate and initially marked the attack as successful and requiring Tier 2 escalation. Reviewing the server response and endpoint evidence helped me understand why neither conclusion was supported.
